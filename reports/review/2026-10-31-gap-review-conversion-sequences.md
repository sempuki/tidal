O1. Same-rank tie-breakers against the rvalue-reference preference (ICS-28, ICS-32, ICS-34, ICS-35). In the source, the tie-breakers for sequences of equal rank sit inside the rank step. They run before the rvalue-reference preference, the function-lvalue preference, the qualification step, and the reference cv step. The page runs ICS-28 and ICS-30 first and the tie-breakers last. A case: the argument is a prvalue of an unscoped enumeration whose fixed underlying type is short. One overload takes an lvalue reference to const short. The other takes an rvalue reference to int. Both bind to a temporary and both are promotions. The source picks the short overload through the fixed-enumeration tie-breaker. The page picks the int overload through ICS-28. A second case: a pointer prvalue, where one overload takes a const lvalue reference to a pointer to void and the other takes an rvalue reference to bool. Probe outcome: the short overload in the first case, the void-pointer overload in the second.

O2. Base tie-breakers against the rvalue-reference preference (ICS-28, ICS-33, ICS-36). The ordering problem of O1 also reaches class and pointer arguments. A case: the argument is a prvalue of class Derived. One overload takes an lvalue reference to const Middle. The other takes an rvalue reference to Base. Both have conversion rank. The source prefers the nearer base, Middle. The page applies ICS-28 first and picks Base. A pointer case: a prvalue pointer to Derived, with a const lvalue reference to a pointer to Base against an rvalue reference to a pointer to void. Probe outcome: the Middle overload, and the Base-pointer overload.

O3. List rules before kind (ICS-21, ICS-22). In the source, the initializer-list preference and the array rules belong to the comparison of two sequences of the same form. The form comparison comes first. So a standard sequence to a scalar beats a user-defined list sequence to an initializer-list specialization. A case: a one-element braced list holding an int, with one overload taking int and one taking an initializer-list of a class that has a converting constructor from int. The source picks the int overload. The page picks the initializer-list overload. This is the Clang reading of Q-0133. The list rules still override rank and the user-defined third-part comparison within one form. Probe outcome: the int overload.

E1. List to a reference whose referenced type matches the element (ICS-20). The page says a braced list always initializes a temporary for a reference parameter. When the list has exactly one element and the referenced type is reference-related to that element's type, the reference binds to the element directly. The direct-binding sequence and the binding restrictions of ICS-12 then apply. Probe outcome: an lvalue reference to int that is not const accepts a braced list around an int lvalue. Against a const lvalue reference overload, the non-const one wins by fewer cv-qualifiers. An rvalue reference to int has no sequence from a braced list around an int lvalue.

E2. How the best user-defined conversion is chosen (ICS-7, ICS-37). ICS-7 says the ambiguous sequence arises when no conversion is better, and points to ICS-37 for "better". The source chooses among the constructors and conversion functions with ordinary overload resolution. The argument's sequence to the constructor's first parameter or to the conversion function's object parameter compares first. The third-part comparison, the template preference, and the constraint preference follow. A case: a source class S with a non-const conversion function to T, and T with a constructor taking a reference to const S. For an S lvalue, the conversion function wins by fewer cv-qualifiers on its object parameter, so no ambiguity arises. If the constructor took a reference to non-const S instead, the two tie and the sequence is ambiguous. Probe outcome: copy-initializing T from the S lvalue is accepted in the first case and rejected as ambiguous in the second.

E3. Qualification step and array bounds (ICS-31). The page says the better sequence is the one that adds fewer cv-qualifiers. In the source, the qualification conversion can also drop an array bound, and the better sequence is the one whose result converts to the other's result by such a conversion. A case: the argument is a pointer to an array of three int. One overload takes a pointer to an array of three const int, and the other takes a pointer to an array of unknown bound of const int. Both add the same cv-qualifiers, so the page finds a tie. The source prefers the known bound. Probe outcome: the known-bound overload.

E4. Explicit conversion functions for a class target (ICS-4). The page says direct initialization adds explicit conversion functions to the class or to a type one qualification adjustment away. For a class target, the source adds explicit conversion functions only in one case. A temporary is bound to the reference first parameter of a constructor of that class, and the constructor is called with one argument during direct-initialization of an object of that class. The qualification-adjustment allowance belongs to non-class targets and to direct reference binding. Probe outcome: direct-initializing a class object from a source that has only an explicit conversion function to the class is accepted. Passing that source to a function that takes the class by value finds no sequence.

E5. Direct binding to a conversion function's result (ICS-4, ICS-11). ICS-4 lists conversion functions that "return a suitable reference" for direct binding. When the parameter is an rvalue reference, or binds a function by lvalue reference, the source also admits conversion functions whose result is a prvalue of a reference-compatible type. A case: a source class with one conversion function returning class X by value, and overloads taking an rvalue reference to X and a const lvalue reference to X. Both sequences use the same conversion function, so their third parts compare. The rvalue-reference binding wins. Probe outcome: the rvalue-reference overload.

M1. Deleted functions (ICS-8). The source ignores whether a function is deleted when it forms a sequence. A deleted converting constructor or a deleted conversion function still forms a user-defined sequence, and the program is rejected only if that sequence belongs to the chosen function. ICS-8 does not list deletion. Probe outcome: a class with a deleted constructor from int, and overloads taking that class and taking an ellipsis. A call with an int chooses the class overload and is rejected.

M2. Function references and conversion function results (ICS-29, ICS-37). When a conversion function result binds directly to a reference to a function type, the source favours a conversion function that returns an lvalue reference when an lvalue reference is bound, and one that returns an rvalue reference when an rvalue reference is bound. The source applies this preference after the third-part comparison and before the template preference. No ICS rule states this preference. Probe outcome: a class with one conversion function to an lvalue reference to a function type and one to an rvalue reference to it. Binding an rvalue reference to that function type picks the rvalue-returning one, and binding an lvalue reference picks the lvalue-returning one.

M3. Equal-rank floating-point types in the reverse direction (ICS-35, ICS-37). The source's equal-rank preference works in both directions. A conversion into floating type A from an equal-rank floating type beats a conversion into A from an integer type or from a floating type of other rank. Different sources only arise when the results of two conversion functions compare. ICS-35 covers only one source going to several targets, and ICS-37 does not list this case. Probe outcome: a class with conversion functions to the 32-bit extended floating type and to double, used to initialize a float, picks the extended-type conversion on an implementation where that type and float have equal rank. The page would report an ambiguity.

M4. Two targets of equal rank (ICS-35). The source has a further condition. When both targets have the source's rank, the target of greater subrank wins. ICS-35 compares only an equal-rank target with an unequal one. Probe outcome: with an extended floating type that has the same rank as double, a double argument passed to overloads for that extended type and for another equal-rank type picks the one of greater subrank. This probe needs an implementation with three types of one rank, so it may not be testable on the matrix.

M5. Reference to an initializer-list specialization (ICS-22). The source states the initializer-list preference for a sequence that converts to the initializer-list type. A parameter that is a const reference to that type reaches the specialization through ICS-20. The page does not say whether ICS-22 covers that parameter. Probe outcome: a one-element list of int, with one overload taking int and one taking a const reference to an initializer-list of long, picks the reference overload.

M6. Constructors removed from the candidate set (ICS-4). The source removes two kinds of constructor from every candidate set. The first is a defaulted move constructor or move assignment defined as deleted. The second is an inherited constructor whose first parameter is a reference to a type between the base and the derived class, when one argument constructs the derived class. ICS-4 lists the converting constructors without these exclusions. The nearest rules may sit in the constructor page instead. Probe outcome: copy-initializing a class from an xvalue of the same class, where its move constructor is defaulted and deleted and a copy constructor takes a reference to const, is accepted and uses the copy constructor.

M7. Designated list to a reference (ICS-18, ICS-20). The source allows a designated list only when the parameter has an aggregate type. A reference to an aggregate is not itself an aggregate type, so the plain reading gives no sequence. ICS-20 sends every non-array reference through a temporary, which would allow it. Probe outcome: a designated list passed to an overload taking a const reference to an aggregate and to an overload taking an ellipsis. The expected result is the reference overload, but a compiler split would belong in Q-0136.

M8. One element of a derived class for a non-aggregate class (ICS-19, ICS-36). The source gives that sequence conversion rank when the element's class derives from the parameter's class. The source does not say whether the nearest-base tie-breaker applies to it. Probe outcome: a braced list holding a Derived lvalue, with overloads taking non-aggregate Middle and non-aggregate Base by value, picks Middle.

M9. Assignment left operand and an explicit object parameter (ICS-10, ICS-13). The source restricts the left operand of any assignment operation to standard sequences, in all contexts. The source also says an explicit object parameter accepts user-defined sequences. The two statements meet for an assignment operator declared with an explicit object parameter. ICS-10 limits the restriction to the built-in assignment, and ICS-13 allows user-defined sequences. Probe outcome: assigning to an object of a class convertible to the parameter's class, through an assignment operator with an explicit object parameter. Record the compiler results either way.

S1. ICS-34 holds two behaviours. ICS-34 defines a promotion (an unscoped enumeration with a fixed underlying type promotes to that type and to its promoted type) and states a tie-breaker between the two. The promotion belongs with the conversion rules that ICS-2 cites. The source also limits the tie-breaker to the case where the two targets differ. Probe outcome: an enumeration whose fixed underlying type is int, against overloads for int and long, picks int by rank alone.

S2. ICS-37 holds two behaviours. ICS-37 mixes a best-function rule (the conversion function whose result needs the better third part wins) with two sequence tie-breakers that hold only when the sources differ. The first is a step in choosing the conversion function and also orders against the template and constraint preferences (E2, M2). The second extends ICS-33 and ICS-36. Probe outcome: a class with conversion functions to Middle and to Derived, used to initialize a Base, picks the Middle conversion function.

S3. ICS-17 holds the string-literal case. The source treats one string literal in braces for an array of characters as its own case, checked before the initializer-list and array cases. A literal of the wrong character type falls through to the element rule and finds no sequence. Probe outcome: a braced wide string literal passed to an overload taking a reference to a const char array and to one taking an ellipsis picks the ellipsis.

S4. ICS-28 exception. The source turns the rvalue-reference preference off when either of the two sequences binds the implicit object parameter of a member function that has no ref-qualifier. The page's wording reads as if the exception concerns only the sequence that would win. Probe outcome: a member function without a ref-qualifier against a non-member taking an rvalue reference to the class, called on a prvalue, is ambiguous. The object-parameter grid already shows this case.

S5. ICS-13 holds three behaviours. ICS-13 defines the implicit object parameter's type, gives the rvalue-binding exception for members without a ref-qualifier, and states that an explicit object parameter is ordinary. The rvalue exception interacts with ICS-12 and ICS-28 and reads better beside them. In the source, an rvalue bound to such a parameter does not change the ranking. Probe outcome: a const member and a non-const member, both without ref-qualifiers, called on a non-const prvalue, pick the non-const member.
